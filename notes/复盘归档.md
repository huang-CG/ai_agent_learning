# 复盘归档（周复盘 / 阶段复盘）

> 用途：归档每次复盘的**过程**（摸底问答要点、执行过程、踩坑、结论），不是只打勾。  
> 新窗口优先看本文件 + `CONTEXT.md` 的复盘日程表。  
> **复盘不评分**（2026-08-01）：不做自评 / Agent 评分。

---

## 复盘执行模板（长期规则）

### 周复盘（固定 2 天）

| 天 | 内容 |
|----|------|
| Day 1 | Agent 提问摸底（约 30 分钟，简答/口述）+ 制定复盘计划 |
| Day 2 | 按计划执行（概念追问 / 代码走读 / 小改造） |

**必交付**：当周知识清单 + 错题/卡点清单 + 1 个小改造（改旧代码）

### 阶段复盘（固定 3 天，含 Day 1 摸底）

| 天 | 内容 |
|----|------|
| Day 1 | Agent 提问摸底（约 60 分钟，简答/口述）+ 制定复盘计划 |
| Day 2 | 按计划执行 |
| Day 3 | 按计划执行 + 收口（口述稿 / 综合小练习） |

**必交付**：阶段能力清单 + 项目口述稿 + 1 个综合小练习

### 通用约定

- 学员每天先报可用时长；Agent 按时长裁剪任务
- 特殊情况可临时调整天数
- 每天至少有一段动手代码，不能只看笔记
- **每次复盘结束后**：把过程写入本文件对应分区（周 / 阶段），并更新 `CONTEXT.md` 复盘日程表

### 单次记录建议结构

```text
### YYYY-MM-DD · 第 N 次（周复盘 / Phase X 阶段复盘）
- 覆盖范围：

- 计划：
- Day2/Day3 执行过程（做了什么、卡在哪、怎么过）：
- 交付物：
- 结论 / 下一阶段先补什么：
```

#### Day 1 · 2026-07-29（摸底 + 计划）

**方式**：简答/口述，非选择题；Agent 提问诊断，学员不必先自评薄弱点。

**摸底要点（过程摘要）**
- Agent vs Chatbot：能说出「能说又能做」；追问后补清「模型决策 → 程序执行」
- ReAct：Thought / Action / Observation / Final Answer；Observation 名字曾忘，功能说对
- `max_steps`：防死循环 / 控 token
- Schema：`description` 管何时调，`parameters` 管怎么传 ✅
- D22 Observation：工具真实结果，不是模型编的
- 短期记忆：对话历史 + trim；长对话超窗口
- 三架构：ReAct / P&E / Reflection 场景大体对；P&E 补了「可重规划」
- D25 评测 10/10 却评 3：能说出「脚手架多、自己动手少」
- D22 vs D27：起初只想到请求体，后补上「循环/解析/编排由框架管」
- `@tool`：对应 Schema 三字段
- 流式：知道 `invoke` 非流式，要改调用层
- `eval` 防护：记混（误以为防括号丢失）→ 纠正为白名单 + 空 `__builtins__`

**掌握分层**
- **稳（A）**：Agent vs Chatbot；ReAct 主流程；Schema 分工；`invoke` vs `stream` 概念
- **半稳（B）**：手写 vs LangChain 职责边界；P&E 细节
- **薄弱（C）**：实现细节断点；术语到函数级映射

**高频卡点**
1. 概念能说，代码位置易卡  
2. 安全细节易混  
3. 框架封装后，容易忽略「框架替我做了什么」

#### Day 2 · 2026-07-31（按计划执行）

**可用时长**：约 2h

**过程**
1. **D22 五函数走读**  
   - 学员能说清 `chat` / `parse_react` / `run_tool`  
   - 纠正：`parse_action` 只拆字符串、不调工具；`run_react` 是主循环指挥官  
   - 追问：无 Final Answer 且无 Action → 直接 return 错误（代码 203–207）✅
2. **D22 vs D27 对照**  
   - 学员答：省请求体/循环/找工具；仍写真工具与密钥  
   - 补全：还省正则解析与长 ReAct 提示词；仍要写 `@tool` docstring、组装、调用方式
3. **D27 流式改造**  
   - 踩坑：`stream` 返回值当 dict 用 → `'generator' object is not subscriptable`  
   - 先走 `stream_mode="updates"`（看节点流程，非整字流式）  
   - 后改 `stream_mode="messages"` 才出现打字机效果  
   - 过程中澄清：`chunk.items()` 只拆顶层；消息是对象用 `.content` 不是 `.get()`  
   - **复盘协作教训**：目标是打字机效果时，应一开始就指明用 `"messages"`，避免弯路  

**当日结论**：五函数职责、框架边界、Agent 流式两模式差异已打通。

---

#### Day 3 · 2026-08-01（按计划执行 + 收口）

**可用时长**：约 2h

**过程**
1. **Schema + 调试回放**  
   - Schema 三字段口述 ✅  
   - 调试：先看是否打算调工具，再看 Action/传参；不调则优先查 description  
   - 传参错优先改 parameters ✅
2. **综合小练习：D27 加 `get_time`**  
   - 第一次失败：system_prompt 只写天气/计算 → 模型声称没有时间工具  
   - 第二次偏航：`get_time(city)` 多余参数 → 反问城市后又调天气  
   - 另：缺 `import datetime`（被「未调用」掩盖）  
   - 修正后验收通过：问「现在几点了？」正确调工具并回答
3. **阶段口述稿**  
   - 学员自述 6 点覆盖完整；纠正 Chatbot 拼写、正则拆 Action 行的表述  
   - 追问：Observation = 程序执行工具结果；get_time 根因 = system_prompt 未声明时间能力  

**最终口述稿（可背）**

> Phase 2 我学了 Agent 和 Chatbot 的区别：Chatbot 只能说，Agent 能通过工具去做。  
> 我掌握了 ReAct：Thought → Action → Observation，不够就循环，够了就 Final Answer；其中 Observation 来自程序执行工具的真实结果，不是模型编的。  
> 我也学会了工具 Schema：`description` 管何时调，`parameters` 管怎么传。  
> 手写版（D22）里我自己写了主循环、正则解析和真天气/计算工具；LangChain 版（D27）框架替我管了循环、解析和编排，我仍要写工具、docstring、组装和调用方式。  
> 复盘里我搞清了流式：`stream_mode="messages"` 才是打字机效果；还踩过坑——工具注册了但 system_prompt 没写，模型就会说自己没有这能力。
