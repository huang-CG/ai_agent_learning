# 复盘归档（周复盘 / 阶段复盘）

> 用途：归档每次复盘的**过程**（摸底问答要点、执行过程、踩坑、结论），不是只打勾。  
> 新窗口优先看本文件 + `CONTEXT.md` 的复盘日程表。  
> **复盘不评分**（2026-08-01）：不做自评 / Agent 评分。

## 复盘执行模板（长期规则）

### 周复盘（固定 2 天）

| 天 | 内容 |
|----|------|
| Day 1 | Agent 提问摸底（约 30 分钟，简答/口述）+ 制定复盘计划 |
| Day 2 | 按计划执行（概念追问 / 代码走读 / 小改造） |

**必交付**：当周知识清单 + 错题/卡点清单 + 1 个小改造（改旧代码）

### 阶段复盘（固定 3 天，含 Day 1 摸底）

| 天 | 内容 |
|----|------|
| Day 1 | Agent 提问摸底（约 60 分钟，简答/口述）+ 制定复盘计划 |
| Day 2 | 按计划执行 |
| Day 3 | 按计划执行 + 收口（口述稿 / 综合小练习） |

**必交付**：阶段能力清单 + 项目口述稿 + 1 个综合小练习

### 通用约定

- 学员每天先报可用时长；Agent 按时长裁剪任务
- 特殊情况可临时调整天数
- 每天至少有一段动手代码，不能只看笔记
- **每次复盘结束后**：把过程写入本文件对应分区（周 / 阶段），并更新 `CONTEXT.md` 复盘日程表

## 当周知识清单（D35–D41 · 定稿）

### 工具选型（D35–D36）

- 答案较恒定、且在知识库内 → **RAG**
- 需要实时/不稳定事实 → **web_search**
- 天气、当前时间 → **专用工具**（省 token、结构化、少跑偏）
- 查库内结构化数据（人数、统计）→ **SQL / Text-to-SQL**

### 文件沙箱（D37）

- 任意路径可能泄露 `.env`；`resolve()` 后 `relative_to(SANDBOX)` 防 `../` 逃出
- 工具必须 **`return`**；`print` 只进终端，模型看不见 Observation

### Prompt / JSON（D38）

- 弱版：JSON 语法能 `loads`，键名可飘（`分类` / `category`），写死 `parsed["label"]` 会炸
- 强版 Few-shot：键名钉死（`label`/`reason`）、类型/枚举钉死、示例合法 JSON、**用户句在 JSON 外**

### LangSmith（D39）

- 成功 Trace 四层：**用户句 → 模型 → 工具 → 最终答**
- 工具层显示的是工具 **`return` 的 Observation**
- 100÷0：模型按原意传参，**工具 `raise`** → 停工具层；传参错是该传 6 却传 5

### MCP vs FC（D40）

- MCP = Model Context Protocol；解决工具被多个 AI 应用重复实现
- FC 与 MCP **不同层**：FC = 模型结构化说「调谁、传什么」；MCP = 发现、连接、复用
- 单 App 自用 → 优先 `@tool`；多端共用 → 再考虑 MCP

### Pydantic（D41）

- D38 靠 prompt **软约束**；D41 **先定 Schema、程序硬校验**，不对 → `ValidationError`
- `class TicketReport(BaseModel)` = **继承**；`TicketReport(label=..., priority=9)` = **创建实例赋值**
- `Literal` 须 `from typing import Literal`

### SQL 只读（D36 · Day2 补）

- `run_sql`：`@tool`，docstring 给模型看
- `execute_select`：内部查库；当前实现 `strip()` + `startswith("SELECT")`，**区分大小写**
- 注释/口头约定 ≠ 代码已实现；要忽略大小写需 `.upper().startswith("SELECT")`

## 当周知识清单（D28–D34 · 定稿）

### Tools / Agent（D28–D29、D34）

- `@tool` 从函数签名 + docstring 生成 Schema 三字段：`name` / `description` / `parameters`
- **description**（docstring 主体）：写「何时用 / 不要用于」→ 模型决定**要不要调**
- **parameters**（ largely 自动生成）：签名给出参数名与类型；docstring 的 **Args** 给每个参数的语义 → 模型决定**怎么填**（如 `query` 填用户检索问句）
- `llm.bind_tools` + `invoke`：模型只返回 **tool_calls 提议**，本地工具**尚未执行**，无 Observation
- `create_agent` 闭环：提议 → **执行工具** → **tool 消息（Observation）** → 模型再生成最终回答
- `result["messages"]` 每条是 **Message 对象**，用 `.type` / `.content`（或 `getattr`），不能用 `message["type"]`
- 典型轨迹（查库题）：`human` → `ai`（提议调工具）→ `tool`（检索结果）→ `ai`（最终答）；`answer` 只是打印标签，不是 message type
- D34：`search_knowledge` 做成工具；`get_current_time` 等非 RAG 工具并存；Agent **按需**查库

### 切块 / Embed（D30–D31）

- **Load**：读 PDF/Markdown（如 `PdfReader` / `read_text`）；先 `path.exists()`
- **Split**：`RecursiveCharacterTextSplitter`；`chunk_size` 小 → 块数**多**，更碎，相关句易单独命中，但也易**丢上下文**
- **chunk_overlap**：相邻块重叠，减轻「切在句子中间」丢语义
- **Embed**：文本 → 向量；**DeepSeek 无 Embedding API**，用**硅基流动** + `OpenAIEmbeddings(model, api_key, base_url)`（接口兼容，Key 仍是硅基）
- **Store / Retrieve**：本机 Py3.14 用 `InMemoryVectorStore` 代替 Chroma（写入崩溃）；`similarity_search(query, k=3)` 取 top-k

### RAG 管道与优化（D32–D34）

- **六步**：Load → Split → Embed → Store → **Retrieve** → **Generate**（Retrieve 只取片段；Generate 交给 LLM 写答案）
- vs **D17 拼 Prompt**：整份文档进 messages → 易超 token、无关干扰多；RAG 只塞 **top-k 相关片段**
- **D32 关键路径**：PDF → 切块 → Embed → 检索 → DeepSeek Generate；无答案要说「文档中没有提及」
- **D33**：metadata（`source` / `chunk_id` / `topic`）；代码侧出处 + 拒编 prompt；`topic=rules` 过滤干扰段；Hybrid Search = 关键词 + 向量（口述）；过期政策更常靠 metadata/业务规则
- **D34**：D32「每次必检索」→ 检索变工具，省 Token、少掺无关段；`VECTOR_STORE` **启动时建一次**，工具内读全局变量检索
